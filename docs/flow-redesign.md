## 一、背景与目标

当前 `dev-plan` 的流程是：主窗规划 → 用户批准 → 派 `develop` → 等子代理 → 审查 → 返工。慢的主要原因不是“代码写得慢”，而是：

1. 每个任务都走相近的完整流程，快速任务被侦察、独立复核、文档环节拖慢；
2. 计划、批准、验收分多次确认，普通实现改动反复等待；
3. 检查顺序倒置：先做昂贵运行验收，晚期才发现语法/契约错误；
4. 主窗在等待期间空等、轮询，或重复读取/重复施工；
5. 汇报只有“完成/未完成”，返工没有严重度，容易无限打磨或漏掉阻塞问题。

P0 的目标：**先消除无效串行、重复确认和晚期返工，不引入重型任务系统。** 通过提示词合同让主窗按风险选最短安全路径、一次批准整个范围、按成本排序验收、非阻塞协作、按严重度返工。

成功信号（观察性，不冒充严格 A/B）：

- 验收项没有减少；
- 快速路径不调用不必要的独立代理；
- 阻塞问题能通过同一 developer 收敛；
- 没有增加文件冲突或漏验；
- 主窗等待时间下降，且不出现“静态检查当真实运行”的误报。

否决信号：总耗时或返工反而上升、上下文不足导致误改、快速路径漏掉必要验收。出现时退回上一级流程，而不是继续加代理。

## 三、现状 → 目标流程

### 现状（0.3.0 之前的行为）

```text
任务进入
  → 固定分档/可能派 recon
  → 给计划
  → 用户批准
  → 派 develop
  → 主窗等待（可能轮询）
  → 子代理汇报“完成/未完成”
  → 主窗审查
  → 返工（可能反复全量返工或无限打磨）
```

问题：路径不随任务变化；批准与验收约定分散；缺少检查成本排序；等待期间行为没有约束；返工没有严重度。

### 目标流程

```text
任务进入
  → 按歧义/影响面/可逆性/可验证性选快速/标准/高风险
  → 只在缺事实时 recon；只在关键歧义时问用户
  → 一次性开工契约：范围 + 非目标 + 允许路径 + 接口/依赖 + 验收 + 检查命令 + 风险/回退
  → 用户批准整个已批准范围（一次）
  → develop 连续完成
      ├─ 子代理：最小切片 → 语法/静态契约 → 针对性测试 → 必要运行/GUI
      └─ 主窗：验收准备、基线审查、资料研究等非冲突工作（不轮询、不重复施工）
  → developer 证据化报告（verified/partial/failed/未验证）
  → 主窗审实际 diff 和关键证据（最终审查责任不外包）
      ├─ 有阻塞问题：send_message 续派同一 developer，附现象/期望/路径/复验项
      └─ 无阻塞问题：交付；非阻塞建议集中记录，不无限打磨
```

`review` 是可选的独立复审，只用于高风险/确有独立复核价值；`scribe` 只在文档属于验收范围或用户需要时调用；`recon` 只在缺事实时调用。主窗始终负责最终审查。

## 四、风险路由矩阵

### 判定维度

| 维度 | 低 | 中 | 高 |
|---|---|---|---|
| 歧义 | 目标、接口、验收都清楚 | 有少量可推断歧义 | 需求/接口/验收不清，猜测会改变产物 |
| 影响面 | 单文件/单模块/局部样式 | 多文件、单模块边界 | 公共机制、跨模块接口、权限、数据、发布 |
| 可逆性 | 易回滚，无副作用 | 可回滚但有迁移/兼容成本 | 删除、迁移、生产配置、强推 Git、密钥/权限 |
| 可验证性 | 有明确命令/人工步骤 | 需要组合检查 | 只能真实运行/GUI/外部环境证明，或证据不足 |

### 路径矩阵

| 路径 | 适用 | 必做 | 可省略 | 不得省略 |
|---|---|---|---|---|
| 快速 | 范围清楚、单文件/小改、可回滚、验证明确 | 简短计划；一次开工确认；develop；developer 自验；主窗审查 | 不必要的 recon、独立 review、scribe、额外方案对比 | 用户开工批准、developer 自验、主窗最终审查 |
| 标准 | 多文件但需求明确 | 必要时 recon 补事实；一次契约；develop；主窗审查；必要时独立 review | 固定 waterfall、每任务 review、每任务文档 | 契约、验收、自验、主窗审查 |
| 高风险 | 公共机制、权限/数据/不可逆、需求模糊 | 澄清；契约；分阶段 develop；独立 review；真实运行/GUI 验收 | 不必要的形式化步骤 | 澄清、契约、独立复审、真实运行证据、主窗审查 |

规则：

1. 只选一条最短安全路径，不固定跑瀑布。
2. 任务变复杂/风险升高时升级路径；任务变简单且证据充分时可降级。证据不足、只能真实运行/GUI 证明或当前无法验证时，只能升级路径并补证据，**绝不因验证困难降低路径等级**。
3. 路径判断写进计划一句话；不把流程当 KPI，不为凑流程派代理。
4. 用户说“直接给计划”时只降规划深度，不自动获得开工授权。

## 五、一次性开工契约与任务书模板

### 开工契约（主窗写给用户/自己）

```text
范围：这次要做什么，边界到哪里
非目标：明确不做什么
允许路径：精确到目录/文件；不允许改动的路径
接口/依赖：要遵守或改变的接口、数据形状、依赖与兼容约束
验收条件：可逐条勾选的通过/失败判据
检查命令：每条验收对应的最小检查命令或人工步骤
风险/回退：主要回归风险、升级路径条件、回滚方式
```

规则：

- 用户批准一次，覆盖整个已批准范围。
- 普通文件编辑和实现细节由 developer 在契约边界内决定，不反复等待主窗/用户批准。
- 只有以下情况重新确认：范围扩大、风险变化、宿主权限要求（沙箱升权、安装/卸载、改 profile、破坏性操作）。
- 用户只说“给计划”时，契约只展示不派工；用户已明确批准开工时，不为同一范围重复请求批准。

### develop 任务书模板（必须自足）

```text
目标：<用户原始请求的关键句 + 本次要达成什么>
非目标：<明确不做什么>
验收标准：
- [ ] <可勾选判据 1>
- [ ] <可勾选判据 2>
允许改动路径：
- <文件/目录>
- 不允许改动：<路径>
接口/依赖：<必须遵守的接口、数据形状、依赖与兼容约束；没有写“无新增接口/依赖”>
检查命令：<对应验收标准的最小命令；无法运行写原因>
风险/回退：<主要风险、停止并报告的触发条件、回滚方式>
完成定义：<代码/测试/文档/不提交 Git 等>
实际变更证据：<完工必须附真实 diff（git diff 或等价 unified diff）；新文件/非 Git 给修改前后内容或可核对等价证据；不能只给文件清单>
汇报格式：按「施工汇报格式」回传

工作区：<绝对路径>
当前状态/相关文件：<简要>
项目规范入口：<AGENTS.md 等>
```

首次派工固定 `name=developer`；后续追问/返工用 `send_message` 给同一 developer，不新建、不换人。任务书不能要求 developer 再向人类提问；缺信息或冲突在汇报中单列并停止相关动作。

## 六、developer 执行与证据报告合同

### 执行顺序（成本从低到高）

1. **最小切片**：先完成一个能证明方向正确的最小可运行/可审查改动。
2. **语法/静态契约**：语法检查、类型/配置/schema、静态合同自检。
3. **针对性测试**：覆盖本次改动和关键回归点的最小测试集。
4. **必要运行/GUI 验收**：只有静态与单测无法证明的行为，才执行真实会话、真实 Host 或 GUI 验收。

不得跳级把“静态检查通过”写成“真实运行验收通过”；没有执行的检查标成未验证。

### 派工事实

主窗写或展示任务书**不是派工**；唯一派工事实是实际调用 `develop`（首次 `name=developer`）并收到工具接受结果。

- 顺序：形成自足任务书 → 实际调用 `develop`（任务书作为 prompt 参数）→ 工具接受后才可说“已派出 developer” → 结束当前回合等自动通知。
- 只有文本任务书、没有工具调用时，不得声称已派出/已返工/已验证。
- `develop` 不可用、调用失败或未发生：报告“未派工”及原因，不输出假装成功的流程汇总。
- 返工同样以实际调用 `send_message` 为准；只写返工文本不算已返工。

这次真实 dev-plan 会话（`session-4ac35a5d-...`）就是该失败模式：主窗输出完整任务书并声称已派出，但日志无 `develop` 调用、无子代理、无产物，`turn/end` 却 completed。该会话只作为回归来源，**不是通过证据**。

### 汇报格式（固定）

```text
1. 改动：文件与目的；没有改什么也写明
2. 真实命令与输出：逐条命令、退出码、关键输出；每项标 verified / partial / failed / 未验证
3. 自验收：对照验收标准逐条写 verified / partial / failed / 未验证
4. 风险：回归风险、未覆盖场景、需要主窗复核的点
5. 假设与未验证项：缺信息、冲突、无法验证的内容
6. 阻塞/需主窗决策：没有写“无”；有则写现象、期望、相关路径与建议
7. 实际变更证据：优先真实 diff（git diff 或等价 unified diff）；新文件/非 Git 工作区给修改前后内容或可核对的等价证据；不能只给文件清单。证据过大给分段/关键片段+完整证据位置
```

### 打断主窗的边界

developer 只在以下情况打断主窗：

- 阻塞：缺关键输入、权限/环境不可用、无法继续；
- 范围冲突：任务书与仓库事实/项目规范/更高优先级指令冲突；
- 关键契约决策：接口、数据、依赖、验收标准需要主窗/用户拍板。

普通实现细节、文件命名、测试命令、局部重构由 developer 自行决定并写进汇报，不频繁请求确认。

## 七、主窗非阻塞、审查与返工规则

### 非阻塞协作

- 依赖子代理自动完成通知；等待期间结束当前回合，不 `sleep`、不循环 `wait_agent` / `list_agents`、不反复确认进度。
- 不重复施工、不替 developer 改代码。
- 不重复读取 developer 正在修改的同一批文件；需要基线时读快照/已批准计划，或等汇报后读最终 diff。
- 可以做的非冲突工作：验收准备、审查基线、资料研究、独立任务；不得修改 developer 的允许路径。
- 不要求频繁进度汇报；没有新证据不反复催问。

### 审查

1. 先核对已批准契约/计划/项目规范，建立验收基线。
2. 审实际 diff、关键命令与证据，不重复整个施工过程。主窗没有 fs/search/Shell/Git 工具，实际变更证据必须由 developer 随汇报提供。
3. 没有实际 diff 或等价证据时只算“摘要审查”：不得写“已核对 diff/变更”，应先 `send_message` 要同一 developer 补真实 diff、修改前后内容或其他可核对证据；补证据仍走同一 developer。
4. 只有高风险或确有独立复核价值时才派 review 读取/证伪；review 只是可选独立复审，不替主窗做最终判断。
5. 按严重度分：阻塞（错误、漏范围、不可回滚、验收失败）→ 重要（回归风险、关键未验证项）→ 建议（风格、可选优化）。
6. 主窗最终审查责任不外包给 review 或 developer。
7. 静态检查全绿不能代替关键运行/GUI 验收。

### 返工

- 阻塞问题用 `send_message` 续派同一 developer，附：失败现象、期望结果、复现命令/路径、重新验收项。
- 非阻塞建议集中记录，交用户决定；不为一两条风格建议无限打磨，不反复全量重跑。
- 同一任务不得同时使用 `develop` 和 `rework_task` / `ask_worker`；返工只走一条通道。
- 没有正确性问题就零问题通过；只有项目规范明确要求或影响正确性才报风格。

### 代理调用纪律

- `recon`：只在缺少事实且事实会改变计划/验收时调用。
- `review`：只在真正高风险、关键事实需证伪、或确有独立复核价值时调用。
- `scribe`：只在文档属于验收范围或用户明确需要时调用。
- 不为凑流程调用；调用成本高于收益时，主窗自己完成允许范围内的静态审查。

## 八、配置与工具影响

P0 **本身不新增任何插件设置项**：

- P0 不新增 `flowMode`、`riskLevel`、`parallelism`、`maxDevelopers` 等流程配置。
- P0 不改变 `settings.js` 的 Config 字段；不改变 `cordis.patch.yml` 的默认配置。
- P0 不新增运行时依赖、不新增工具、不新增代理类型、不开启 Team、不引入 DAG。
- 不改变四个委派工具的 `spawn / maxDepth=1 / modelSelection=false / modelDiscovery=false / agentOptions` 合同。
- 不改变模型守门 `pin / audit / off`、`killOnViolation`、`honorExplicit`、`audit` 的判定语义。
- 不默认双 developer；不自动降低模型/推理档位。

后续版本在本合同之外新增了设置能力：`developMode` 接受任意宿主预设、provider/model 改为目录联动选择、新增 `guardAllSubagents`（默认 `false`，只守 `dev-plan` 父会话派出的子代理）。这些改动与本合同共存，但不算 P0 流程提效的实现；本文档不据此扩大 P0 的验收口径。

实现落点：`preset.js` 的 persona 文本；`README.md` / `detail.md` 的用户说明；`docs/flow-redesign.md` 本合同；测试与自检中的 P0 断言与变异。

## 九、可测试的行为断言

以下断言必须由 `node --test` 和/或 `verify-presets.mjs` 覆盖；文本标记断言必须有对应负向变异，防止以后退化。

### P0-1 风险分级

- persona 同时包含“快速路径 / 标准路径 / 高风险路径”。
- persona 同时包含四个判定维度：歧义、影响面、可逆性、可验证性。
- persona 明确证据不足/只能真实运行证明时提高风险等级或补证据，**绝不因验证困难降低路径等级**。
- persona 明确“快速路径不取消用户开工批准、developer 自验和主窗审查”。
- persona 明确“只选一条最短安全路径，不固定跑瀑布”。

### P0-2 一次性开工契约

- persona 含“一次性开工契约”。
- 任务书含：范围、非目标、允许路径、接口/依赖、验收条件、检查命令、风险/回退。
- persona 明确“普通文件编辑和实现细节不反复等待批准”。
- persona 明确只有“范围扩大、风险变化或宿主权限要求”才重新确认。

### P0-派工事实（真实失败回归）

- persona 含“文本不是派工”“必须实际调用 develop”“只有工具接受后才可说‘已派出 developer’”“未派工”“任务书是 develop 的 prompt 参数”。
- persona 明确“不得停在计划、前言或任务书文本”“实际调用 send_message”才算返工。
- 反向断言：不允许“文本也能算派工”“没有调用也可以说已派出”“文本任务书即视为已派工”。
- 回归来源：2026-11-18 真实 dev-plan 会话只输出任务书文本、无 develop 调用/子代理/产物，`turn/end` completed；修复后必须用新会话验证实际工具调用，不能把该失败会话写成通过。

### P0-3 验收前置与成本排序

- persona 含“最小切片”“语法/静态契约”“针对性测试”“必要运行/GUI 验收”，且顺序正确。
- persona 含“静态检查不等于真实验证”。
- 汇报要求每项检查标 verified / partial / failed / 未验证。

### P0-4 非阻塞协作

- persona 含“非阻塞协作”。
- 明确“不轮询”“不忙等”“不重复施工”“不重复读取 developer 正在修改的文件”。
- 明确 developer 只在阻塞、范围冲突、关键契约决策时打断主窗。
- 明确主窗等待期间可做非冲突工作，且不修改 developer 的允许路径。

### P0-5 证据化报告与严重度返工

- 汇报含改动、真实命令与输出、自验收、风险、假设与未验证项、阻塞项、实际变更证据。
- 实际变更证据优先真实 diff；新文件/非 Git 工作区提供修改前后内容或可核对等价证据；不能只给文件清单。
- persona 明确主窗审“实际 diff 和关键证据”；只有摘要/文件清单时不得声称审过实际 diff，应先 send_message 要同一 developer 补证据。
- persona 明确“阻塞问题”续派同一 developer；“非阻塞建议”不无限打磨。
- persona 明确“主窗最终审查责任不外包”。

### 核心约束不回退

- 主窗自身永不亲自写代码；主窗仍不挂施工工具。
- 首次 `name=developer`；同一任务 `send_message` 续派；不反复新建。
- `develop` 不与 `rework_task` / `ask_worker` 混用。
- `recon` 仅缺事实；`review` 仅高风险/确有需要；`scribe` 仅文档属于验收或用户需要。
- 四个委派工具合同保持原样；模型守门 pin/audit/off 与 kill/honor/audit 语义保持原样，默认范围收窄到 dev-plan 子代理（全局开关 opt-in）。
